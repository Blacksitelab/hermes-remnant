## Decisions

### S-010: canonical containment at every indexing entrance

Reuse pathlib, existing exclusion rules, and path_in_profile_scope. Remove the lexical escape fallback from `_relative_path`; outside-root resolution is rejection, never a source_id. Preserve its valid missing-inside-root path behavior (the existing unit test uses one); callers must separately require an existing regular file before reading.

For index_file, index_vault (including its pre-hash shortcut), and _walk_markdown, resolve against the canonical configured root and reject escapes, broken links, and symlink loops before hashing, reading, embedding, entity extraction, or adding an accepted seen-path entry. Skip a rejected link; an actual unreadable/incomplete directory scan must retain the existing failed-scan/no-reconciliation behavior. Handle ValueError, OSError and resolution-loop errors intentionally rather than crashing the scan or converting them to lexical paths.

Allow stable in-vault symlinks only when both the lexical entry path and the canonical target satisfy exclusions and configured scope. This prevents an excluded folder alias exposing an allowed target and an allowed alias exposing a private target. Canonical relative paths remain the storage identity (matching today's successful resolve branch), deduplicated during a scan; do not create alias duplicates. A configured vault-root symlink establishes the trusted canonical root; it is not a descendant escape.

Hash/read the validated canonical target, not the original symlink alias. Validate again at the actual read boundary so a retargeted alias cannot bypass the walker's decision. Keep unchanged-file embedding repair inside the same validation boundary. This addresses resolved-path/alias escapes; it is not a promise of a race-free sandbox against an adversary concurrently replacing canonical ancestor directories. Do not advertise that stronger guarantee or implement a new filesystem sandbox in this patch. Record that residual assumption explicitly in docs; if the repository's actual required threat model includes hostile concurrent directory mutation, stop and escalate for descriptor-relative no-follow design rather than claiming it solved.

No automatic deletion of historical leaked rows. A successful scan may apply existing owner/scope-scoped forgotten reconciliation; unavailable roots/unreadable subtrees must not cause mass forgetting. Operator investigation/cleanup of previously indexed outside content needs separate authorization, because its original provenance cannot always be reconstructed safely.

Relevant source: vault.py:_relative_path, index_file, index_vault, _walk_markdown; existing tests/test_phase4.py and tests/test_profile_isolation.py.

### S-011: scope the graph itself, then validate candidates using stored policy

Reuse effective_profile_scope, visibility_allows, the existing SQL path predicate and search filters. Preserve the existing distinction between no restriction (`None` at the retrieval boundary), configured/requested scope intersection, and an empty effective scope. Tool arguments may narrow but never broaden configured scope. No new graph tool arguments are needed.

1. tools.py:memory_graph passes `config.profile_scope or None` to graph_traverse. The RecallRequest/common service also observes configured scope, independent of whether an adapter supplied it.
2. db.py:traverse_graph applies owner, active status and effective path scope to seed eligibility, each relation's supporting memory (both relations.source_memory_id and relation_evidence.memory_id), returned memory rows, and exposed entity eligibility. Hidden-only seed -> entity=None, entities=[], memories=[]. A hidden-only connecting edge must not reveal or bridge to another node. An entity supported by an authorized incident edge or authorized linked memory may be exposed; never return a node supported only by excluded data. Preserve depth and evidence_only behavior and the current restricted seed metadata shape.
3. The shared RecallService candidate boundary reads canonical stored authorization fields by ID in a batch: owner, status, visibility, source, type, source_id. Adapter-supplied/missing source or type must not bypass document scope. Reuse current helpers rather than copy path/visibility rules into each adapter. Rehydrate authoritative content/provenance for accepted IDs so forged policy/content fields and pre-attached claim_group data cannot be presented as stored evidence; preserve only actual ranking/discovery annotations needed by existing lanes. Unknown/deleted IDs fail closed. Pending turns come only from the existing scoped pending-overlay loader; do not trust externally supplied pending=True as an authorization bypass.
4. Preserve legitimate superseded-memory historical recall: active rows normally; superseded rows only for the existing claim-aware historical/date query intent. Do not replace this with blanket active-only filtering. Reuse/extract the existing intent predicate if necessary, keeping search and candidate policy identical; no new historical feature or intent heuristic. Inactive/forgotten rows never return. Visibility ceiling remains the existing one, not a new cross-owner sharing model.
5. Final claim grouping must contain only authorized inputs. Graph entity metadata bypasses RecallService today, so fixing only candidates is insufficient.

The SQL path helper currently uses LIKE without literal wildcard escaping and SQLite's default case folding, whereas the Python helper uses literal prefix matching. Make that shared SQL predicate agree with the existing Python normalized, case-sensitive, slash-boundary semantics for `%`, `_`, backslashes, and mixed case; reuse a parameterized literal comparison (e.g. equality/substr), not a new matcher. Cover this in the same scope regressions, since using the uncorrected SQL predicate for metadata authorization would leave a bypass.

### S-012: WAL only on recognized fixed runtimes; safe fallback without live conversion

Primary source verified during planning: https://sqlite.org/wal.html#walresetbug (page reports update 2026-08-25). Upstream identifies SQLite 3.7.0 through 3.51.2 as affected, with fixes in 3.51.3+ and backport release lines 3.44.6 / 3.50.7. The race requires multiple connections writing/checkpointing the same WAL file. The upstream page now links an August 2026 external reproducer; this project has not run it. A passing integrity_check is not proof against this race.

Implement a small shared connection-journal policy helper in remnant/db.py, used by existing writable Remnant DB entry points. No extra package or force-unsafe configuration switch.

- Recognized fixed upstream versions: >=3.51.3, 3.44.x with patch >=6, and 3.50.x with patch >=7. Do not treat >=3.44.6 or >=3.50.7 as unbounded safe ranges; that would admit affected intermediate branches. Read the linked SQLite engine version, not the Python/sqlite3 module wrapper version or command-line sqlite executable.
- Fresh/non-WAL DBs on affected or unverified runtimes use DELETE with synchronous=FULL. Keep current WAL/NORMAL behavior only on recognized fixed runtimes. Verify the actual pragma result; an unsupported mode, refusal or lock error must fail clearly and close the new connection, never silently continue in unsafe WAL or OFF mode. Handle :memory: explicitly (SQLite returns memory); it is not a persistent multi-process WAL DB.
- If an affected/unverified runtime opens an existing WAL DB, refuse initialization BEFORE application writes, migrations, checkpoints, or a journal-mode change. Close the connection and raise an actionable RuntimeError identifying engine version, current journal mode and the need for an operator-approved patched runtime or offline conversion. No automatic WAL->DELETE transition: acquiring SQLite's conversion lock is not a substitute for coordinated process shutdown, especially with old clients that may re-enable WAL.
- Vendor backports can retain an older numeric engine version. Treat those as unverified, not proven vulnerable: DELETE remains supported without a minimum-version install requirement. Do not guess from OS release, compile_options, package strings, or a green integrity_check. If an operator needs WAL for a vendor build not recognized above, require authoritative exact-build evidence and a separately reviewed safe-build recognition change (or a recognized upstream runtime). No blanket version bypass knob is included.
- Log selected fallback/rejection reason without content/secrets; document lock-contention/performance tradeoff and the compatibility impact on existing WAL installations. Do not promise a throughput level without measuring it.

Root-cause coverage includes reextract.py's second unconditional WAL pragma plus direct writers calibrate_trust.py and classify_relations.py, which can write an already-WAL file without going through RemnantDB. Apply the shared guard before their first write; their dry-run paths must not change journal modes. Preserve existing transaction semantics. Trace maintenance backup/restore and recover.py: private destination files/read-only sources are different from a shared writable live DB; retain safe backup semantics, validate restored output mode before returning it as writable, and never checkpoint an unsafe shared source. No standalone global connection factory or broad CLI refactor is needed.

Proposed helper interface: `configure_sqlite_journal(conn, *, allow_mode_change=True) -> str`. This is new, not an existing API. It owns journal/synchronous safety only, not opening connections, migrations, row_factory or foreign_keys. `allow_mode_change=False` checks safety without mutating journal/synchronous settings for dry-run clients; affected/unverified existing WAL still fails closed. Caller closes its connection on policy failure. Tests may inject/patch the narrow version classifier, never claim that simulating a version upgrades the actual linked engine.

Operational policy (documentation only): all clients sharing a DB must be stopped and legacy writers prevented from re-enabling WAL before conversion or runtime changes. Use a verified backup and patched tooling for any approved checkpoint/conversion; keep sidecars, never delete -wal/-shm as a workaround. Check backup, schema and reopen behavior on a disposable copy first. User owns authorization, timing and final acceptance. No migration/schema bump or runtime install is required by the source patch.
